# AGENTS.md

Rules for anyone — human or AI agent — changing CircuitTimer. `CLAUDE.md` only points here.

## Core rules

1. **Platform:** iOS 17+, Swift 6 language mode with complete strict concurrency, Xcode 27.1. The package declares watchOS 10 for the watch app; only the modules it links build for watchOS (`make build-watch-package`).
2. **Versions:** read them from `CircuitTimerKit/Package.resolved` and, for the snapshot tests' SnapshotTesting, `CircuitTimerSnapshotKit/Package.resolved`; never assume an API exists.
3. **Design system:** UI uses `DesignSystem` tokens only. The app is dark only (`UIUserInterfaceStyle = Dark`): color tokens carry the original app's palette, one universal value each, and every package `#Preview` sets `.preferredColorScheme(.dark)`; the Live Activity keeps the same dark palette whatever the system theme. Literal or system colors and fonts (`Color.red`, `.foregroundStyle(.secondary)`, `.font(.headline)`, `UIColor`) fail lint outside `Sources/DesignSystem/`. The `AccentColor` assets of the app and the watch app and the fill of `LaunchLogo.svg` mirror the `Brand` token, and `LaunchBackground` mirrors `.surface(.screen)`; change them together.
   - Fonts ship in `Sources/DesignSystem/Resources/Fonts/` with their license and are registered at runtime from `Bundle.module`; `Font.custom` lives only in `DesignSystem`.
4. **Dependencies:** reach the outside world through `@Dependency` clients, read by key path. No singletons, no static mutable state. A new client, key or storage strategy also gets a value that is not live in `AppScenario.prepare` (see UI tests); `make lint` fails without one, as long as a key's declaration keeps `DependencyKey` on its first line. It cannot see our own `SharedKey`s: a new one needs its default store replaced there by hand.
5. **Navigation:** state-driven — `@Presents` + `@Reducer enum Destination` for modals, `StackState` + `@Reducer enum Path` for pushes. A feature never knows its container; it talks up only through `delegate` actions. A pushed screen that must not close unasked hides the system back button: a SwiftUI pop reaches the reducer as `popFrom`, which removes the element without a veto.
6. **Every commit passes `make verify-clean`.** A squash-merged pull request may run it at milestones instead; its last commit always passes it.

## Engineering principles

- **High cohesion, low coupling.** A module owns one context and is reached through a narrow interface.
- **Earn every abstraction.** Add a layer only for a need you can name today; prefer duplication over the wrong abstraction.
- **Cut indirection, not file count.** Remove forwarding-only wrappers; keep the split by concern.
- **Build on what exists.** Reuse the project's mechanism instead of a hand-rolled copy.
- **Handle every error explicitly.** Loud for developers (`os.Logger`), graceful for users (a visible state). Never an empty `catch`, never a dropped `try?`.
- **Pin behavior with tests before changing it.** A test must fail when the behavior it guards breaks.
- **Debug from evidence.** Reproduce, observe the real values, fix the cause, add a regression test.
- **Read what goes stale.** Check versioned API facts in the source instead of recalling them.

## Module map

Two local packages. `CircuitTimerKit` holds the app's modules; every module is a library product, so the package scheme builds all of them. `CircuitTimerSnapshotKit` holds only `SnapshotCapture` for the snapshot tests; the app, the widget and the watch app never link it. The app target in `CircuitTimer.xcodeproj` composes `AppFeature`, configures TipKit and calls the injected `BackgroundNotificationClient.installForegroundSuppression` at launch; its `AppDelegate` runs `AppFeature`'s `ProcessTeardown` when iOS terminates the app. In Debug it builds the store from a UI test scenario of `AppScenarios` when the launch asks for one. The UI test target `CircuitTimerUITests` in the same project links only `UITestContract`. The app imports `BackgroundNotifications` and `WorkoutActivity` (its AppIntents package), and in Debug `AppScenarios`, `UITestContract` and `WorkoutStorage` (for the CloudKit schema initializer); TCA reexports Dependencies for the hook. The widget extension `CircuitTimerWidgets` draws the Live Activity from `WorkoutActivity` and `DesignSystem` only; lint covers it like the package. The watch app `CircuitTimerWatch` (watchOS 10, bundle `WATCH_BUNDLE_ID`, companion of the app) links only `WatchRemoteFeature` and shows its `WatchRootView`; the app target depends on it and embeds it in `CircuitTimer.app/Watch/`, so every build of the app builds it too. Its shared scheme `CircuitTimerWatch` runs it on a device; lint covers it like the package. The snapshot tests `CircuitTimerSnapshotTests` run inside `CircuitTimerSnapshotHost`, an empty app of the same project that links no module and never configures TipKit; the tests link `SnapshotCapture`, `AppFeature`, `WorkoutEditorFeature`, `WorkoutTimerFeature`, `WorkoutDomain`, `WorkoutActivity`, `WorkoutHealth`, `WorkoutStorage`, `BackgroundExecution`, `BackgroundNotifications` and `CloudSync`, and the screen tests also `SettingsFeature`.

Layering:

- `*Feature` → `DesignSystem`, `WorkoutDomain`, `WorkoutStorage`, `WorkoutActivity`, `WorkoutHealth`, `TimerPreferences`, `BackgroundExecution`, `BackgroundNotifications`, `CloudSync`. A feature never imports another feature; composition happens in `AppFeature`.
- Features import `UITestContract` only for accessibility identifiers. `AppScenarios` is all under `#if DEBUG`, so Release links it empty; only the app imports it, in Debug, and it imports features only for their clients.
- `BackgroundExecution` owns background-task assertions shared by `AppFeature` and `WorkoutTimerFeature`; it imports no feature, TCA, or workout module.
- `BackgroundNotifications` imports no feature, TCA or workout module; the app and the timer use only its dependency client.
- `AppFeature` reads `TimerPreferences` to gate the first Start permission request.
- `SettingsFeature` needs no workout module and imports none.
- `WatchRemoteFeature` is the watch app's feature: no iPhone feature imports it, and it imports none.
- `CloudSync` imports no feature, TCA or workout module: `WorkoutStorage` asks it how to open the store, `AppFeature` reads its remote changes and Settings its status and switch.
- `TimerPreferences` depends only on Sharing: Settings writes the timer preferences and the timer reads them, so neither feature imports the other.
- `WorkoutTimerFeature` reads no workouts: `AppFeature` hands it a `WorkoutSchedule`. Of `WorkoutStorage` it uses only `WorkoutRunRecordClient`, to save its own run.
- `WorkoutDomain`, `WorkoutStorage` and `WorkoutHealth` never import TCA or SwiftUI. `WorkoutDomain` depends on none of our modules.
- `WorkoutActivity` imports `WorkoutDomain` and no feature, TCA or SwiftUI. iOS limits an activity's attributes and state to 4 KB together, so `ContentState` carries a stage, its boundary dates and the next stage plus an ephemeral `controlGeneration`, never a whole `WorkoutRun`. App and widget declare `AppIntentsPackage` roots. `WorkoutActivity` is linked statically, so the build merges its metadata into each host; do not re-export it through `includedPackages`: on iOS 17.5 that caused action lookup to return no metadata (checked with Xcode 27.1). The timer syncs it, `AppFeature` ends what earlier processes left, and `CircuitTimerWidgets` draws it and routes buttons through its intents.
- `WorkoutHealth` imports none of our modules. Its iOS 26 calls stay inside the live client, so reducers never branch on the OS version. The timer starts its session, reports its run's track and ends it with the final track, `AppFeature` asks for access and ends what earlier processes left, and the app delegate ends every session at termination.

- `SnapshotCapture` imports none of our modules; only `CircuitTimerSnapshotTests` links it. Of our code only `SnapshotCapture` imports SnapshotTesting.

## Delivery

- A tag `v<MARKETING_VERSION>` (or `v<MARKETING_VERSION>-<suffix>` for another build of the same version) on a commit of `main` whose CI passed runs `testflight.yml`, which archives and uploads to TestFlight. The build number is the UTC start time, `YYMMDD.HHMMSS`.
- The archive is built unsigned: an App Store Connect API key signs only at export, with a cloud-managed distribution certificate, so the key needs the Admin role. The export keeps only the entitlements of the archived signature, so `make archive` then signs the widget, the watch app and the app ad hoc, in that order and the watch app without entitlements, the app with `Configs/CircuitTimer.entitlements` and the container from its Info.plist; ad hoc signing during the archive itself fails, as an iOS app with iCloud entitlements requires a profile. `testflight.yml` checks the archive for `NSSupportsLiveActivities`, the extension, the watch app (`WKApplication`, the app as its companion, the app's version and build), the `remote-notification` and `workout-processing` background modes, both Health usage texts in English and Russian, the container, HealthKit and its other ad hoc entitlements and, with `make check-release-app`, the absence of UI test scenarios, then confirms that the app, `CircuitTimerWidgets.appex` and `CircuitTimerWatch.app` carry App Store signatures of the team, the app with the container, CloudKit, the Production CloudKit environment, production Push and HealthKit in its signature and profile, the widget and the watch app without HealthKit or iCloud, in a separate signed IPA export, because the upload leaves no exported files to read (`scripts/verify-export-signing.py`, run with `python3 -I`). These checks run before the upload, so a wrong signature or a failed check stops the run with nothing uploaded and the reports kept as a run artifact; re-running it archives and uploads under a new build number. The upload signs again on its own, so a passing check is strong evidence about the uploaded build, not a proof.
- `Configs/App.xcconfig` holds the bundle IDs (`APP_BUNDLE_ID`, `WIDGETS_BUNDLE_ID`, `WATCH_BUNDLE_ID`), `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` for the app, the widget and the watch app: App Store Connect flags an embedded bundle whose version differs from the app's.
- `ExportOptions.plist` repeats the team ID from `App.xcconfig`; change both together.
- `claude-review.yml` reviews a pull request from this repository with `claude -p` through the pinned superpowers plugin (its `requesting-code-review` skill) when it is opened, reopened or marked ready for review, and again on the `claude-review` label, which the run removes; every review is a new comment that names the reviewed commit; the prompt is `.github/claude-review.md`. It needs the `ANTHROPIC_API_KEY` secret from the Console organization that receives the Max plan's monthly API credits. It is not a required check.

## Toolchain

- CI pins Xcode 27.1 on the `xcode-27` runner image, still a GitHub preview. Tests run on the iOS 27.0 simulator that the image ships. CI boots the simulator before the tests, and `scripts/run-tests.sh` runs them once more when the test runner hangs before connecting and the result bundle holds no test, which the preview image's simulator sometimes does; a failing package test is not retried. After the package tests CI builds the app with its UI tests in a step of its own, also when they failed, and runs the UI tests on the same simulator. After the UI tests CI builds `CircuitTimerSnapshotKit` strictly, builds the watch app's modules strictly for a generic watchOS Simulator destination with the image's watchOS SDK (no watchOS runtime is installed, locally or there, and none is needed), builds the snapshot tests and runs them on the same simulator, each in a step of its own and also when earlier tests failed; the snapshots run when their build succeeded, whatever the strict build of the package reports. `scripts/report-test-results.sh` reports every bundle in `.build/TestResults/`: failures as annotations, tests that passed only on a retry as warnings, and in the step summary the 20 tests with the most own time. Tests run in parallel, so most of a test's total time is waiting for the others in its process; own time is estimated from the start and length of each test in the bundle's action log. A failed run, or one with a flaky test, keeps the bundles and logs as an artifact. Only runs on `main` save the package sources and DerivedData to the cache, and a Linux job then deletes all but the newest DerivedData cache, which keeps the repository under GitHub's 10 GB. Both workflows key their caches on all three lockfiles, and the DerivedData cache includes the snapshot builds. The `lint` job runs on Ubuntu in SwiftLint's own Docker image, which has the SourceKit our custom rules need, so it takes none of the plan's five concurrent macOS jobs; it also runs `make test-scripts`, so the scripts' tests run with GNU tools and mawk as well. Scripts run with bash 3.2 and with BSD or GNU tools and mawk. After switching Xcode run `make resolve` and `make check-resolved`, then commit **all three** `Package.resolved` files (`CircuitTimerKit`, `CircuitTimerSnapshotKit` and the project's): newer Swift tools pick different package manifests and resolve a different graph.
- SnapshotTesting is pinned to an exact version in `CircuitTimerSnapshotKit/Package.swift`, whose target uses it, so no manifest declares an unused dependency, and to the same exact version in `project.pbxproj`; `CircuitTimerKit/Package.swift` does not declare it. The project's reference deliberately links no product: do not add one. A version bumped in only one of the two places makes the project's joint resolution fail on conflicting exact versions, so change both together, only together with re-recording and reviewing every reference in the same pull request, and run `make resolve` and `make check-resolved`. Its manifest also names swift-custom-dump and swift-syntax for products we do not use; wherever they are pinned, they match `CircuitTimerKit`'s pins.
- Warnings are errors everywhere we control them. The app target sets `SWIFT_TREAT_WARNINGS_AS_ERRORS`. The package turns on `.treatAllWarnings(as: .error)` only when `CIRCUITTIMER_STRICT_WARNINGS=1`, which `make test`, `make build-package` and `make build-watch-package` set. `CircuitTimerSnapshotKit` uses the same `CIRCUITTIMER_STRICT_WARNINGS` switch; `make build-snapshot-kit` sets it, and the project's build of the snapshot tests does not. When the app builds the package as a dependency, Xcode passes `-suppress-warnings`, and the two flags conflict. Strict and non-strict builds use separate DerivedData because the evaluated manifest is cached there.
- Locally, tests and screen checks use only four simulators: `iPhone 17` (`DESTINATION`), `iPhone 17 #2` and `iPhone 17 #3` on iOS 27.0, and `iPhone 15` on iOS 17.5 for checks on the oldest supported iOS. One job runs on a device at a time; a parallel job takes a free one, for example `make test DESTINATION='platform=iOS Simulator,name=iPhone 17 #2,OS=27.0'`, or waits. Create no other simulators; if one of the four is missing, recreate exactly it.
- Parallel UI test workers (`UI_TEST_WORKERS` above 1) make Xcode clone the simulator, so `make test-ui` allows them only with `CI=true`. Locally, UI tests run in parallel only on different allowed simulators, each `make test-ui` with its own `DESTINATION`, and only after one run on each has finished alone: the first run resolves the shared package checkouts, which later runs only read.
- A failing UI test runs once more (`-retry-tests-on-failure -test-iterations 2`); one that passes only then is reported as flaky and keeps its result bundle as an artifact. Package tests get no retry. A UI test fails after 60 s, or after its own `executionTimeAllowance` up to 120 s.
- The launch screen, the `remote-notification` and `workout-processing` background modes and `CTCloudKitContainerIdentifier` live in `Configs/Info.plist`, which Xcode merges with the generated `INFOPLIST_KEY_*` keys. The file is not a member of any target: Copy Bundle Resources would conflict with the generated plist.

## TCA

TCA is built with the `ComposableArchitecture2Deprecations` trait, so APIs going away in 2.0 are unavailable.

```swift
@Reducer
public struct SomeFeature: Sendable {
    @ObservableState
    public struct State: Equatable, Sendable {}

    public enum Action: ViewAction, Equatable, Sendable {
        case view(View)
        case `internal`(Internal)
        case delegate(Delegate)

        @CasePathable public enum View: Equatable, Sendable {}
        @CasePathable public enum Internal: Equatable, Sendable {}
        @CasePathable public enum Delegate: Equatable, Sendable {}
    }

    public var body: some ReducerOf<Self> { … }   // dispatches to `reduce(into:_:)` per action group
}
```

- Views are `@ViewAction(for:)` and only `send` actions; no logic in `body`.
- Presentation goes through `$store.scope(\.$destination, action: \.destination).<case>`. An alert without actions is a plain `case alert(AlertState<Never>)`; a confirmation dialog or an alert with actions is a `@ReducerCaseIgnored` case with a hand-written `Destination.Action`, otherwise the scoped binding drops the chosen action (see `WorkoutEditorFeature`).
- A pushed screen with no state or effects of its own is a `@ReducerCaseIgnored` `Path` case that carries its data; its view sends the stack owner's actions (see `SettingsFeature`).
- The workout editor is the `editor` case of `AppFeature.Path` on the Workouts stack. It hides the system back button, which also turns off the edge and content back gestures on iOS 17 and 26, so it leaves only through `backButtonTapped`; a Workouts tab re-tap sends it the same action, but only while it is read-only.
- The editor has phases: `new`, `viewing` (a saved workout, read-only) and `editing` (after the pencil). `workout` is the workout exactly as stored and is what plays; `original` is the base of the draft, with the rounds lifted into the editor's range. A save returns to `viewing`. Start sends `startRequested` with `workout`; `AppFeature` waits for notification permission and Health access when needed, validates the same viewing workout before presentation and calls `cancelStart()` if that intent is cancelled; it presents the timer only into an empty destination and empties the Workouts stack once the cover has appeared.
- The editor's Save flags read the comparable draft (names trimmed), so spaces around a name are no change; a changed stage that would not play keeps Save dimmed, and `saveBlocker` says why. A stage duration's typed text and its last accepted text live in `StageDurationField`, which sends each accepted edit synchronously from `NumericTextField`'s native edit callback, so Back and Save never miss the last digit; focus never reaches the reducer. The field's tokenizer treats each character as a word boundary, keeping taps between digits in place, and `StageDurationText` maps the caret through the MM:SS mask. Native duration fields use a view-local selected stage ID; only SwiftUI name fields register with `FocusState`, so each input has one responder owner. TipKit has three points: the app configures it, the view shows `SaveWorkoutTip`, and the reducer invalidates it through `SaveTipClient` after a tap on the dimmed Save, hiding it at once with `saveTipSuppressed`. The view sends `layoutChanged` from `.task(id: phase)` and when the keyboard goes; the reducer clears `hasSettled` and sets it again after `tipSettleDelay` on `continuousClock`, by generation, so the tip never points at Save while the screen moves. Tests that send `layoutChanged` use a `TestClock`. Leaving a name field sends `nameFieldLeft` or `stageNameFieldLeft`, and the reducer trims the name before a pending Back or Save arrives.
- The workout timer is the `timer` case of `AppFeature.Destination`, a full-screen cover. Like the editor it closes itself with `dismiss()`, the accepted exception to talking up only through `delegate` actions. Every close path first ends the screen's `TimerSessionClient` session, workout session (with the run's final track, which Health saves), `CueClient` owner, notification owner and Live Activity owner, so a clock loop that starts after the teardown returns before it sleeps. The container never replaces or nils a presented timer; if anything else dismisses the cover, it ends all five owners afterwards, which drops the keep-awake vote, ends the session with the timer's last track, stops cue output and removes the activity.
- The timer owns its own stack, `WorkoutTimerStack`; the stage list is a `@ReducerCaseIgnored` case of `WorkoutTimerFeature.Path` that carries a `WorkoutOutline`. Opening it pauses a running stage or drops a 3-2-1, and leaving it keeps the run paused.
- Long-running or replaceable effects get a `CancelID`; reloads use `cancelInFlight: true`.
- Catch `CancellationError` before the generic `catch` — cancellation is not a failure.
- Clocks, dates and UUIDs come from `@Dependency` (`continuousClock`, `date`, `uuid`); lint rejects `Date()` and `UUID()`.
- Reducers call only synchronous generator dependencies: `uuid`, `date`, `continuousClock` (`now` for an anchor), `nextRevision` of the run record and of `liveActivity`. The single exception with an effect on the outside world is `backgroundTask.begin`, used by the timer and by `AppFeature` around record writes: a `.run` effect starts as a later main-actor task, and the app can be suspended before it runs, so the assertion is taken in the reducer and the effect returned in the same pass ends it. Don't copy this for anything else.
- Bridge callback APIs through an `AsyncStream` that the effect stays suspended on; never let `send` escape the effect.
- Add only the action groups a feature needs (the root feature has no `Delegate`).

## Screens

- A stack that keeps the tab bar to its root puts `tabBarOnlyOnRoot(isPushed:)` on the root, under `tabBarOnlyOnRoots()` on the `TabView`; the Workouts stack does. Before iOS 26 the root hides it through SwiftUI, as hidden by the pushed screen it would come back only after the pop, and a bottom panel on a pushed screen stands on the home indicator's inset so it doesn't drop when the bar goes at the end of the push; no root has a bottom panel. On iOS 26 SwiftUI's tab bar ignores `hidesBottomBarWhenPushed`, so `TabBarRidesWithRoot` carries a picture of the bar away with the root, hides the bar through UIKit and covers it for a moment after the pop while its glass settles. The picture lies in the root's own view, so it moves with it; UIKit logs that a `_UIReplicantView` in a `UIHostingController.view` is not supported, which is accepted. Measured on iOS 17.5 and 26.5 only, not on 18–25. With the bar gone from the workout screen, a Workouts tab re-tap no longer reaches it from the UI; the reducer still handles it.
- A horizontal swipe on a tab's root turns to the neighbouring tab, as a tap on it would: `onPageSwipe` on each tab's navigation stack puts a UIKit pan on the tab's controller view, so the navigation bar and the whole screen take it, while pushed screens keep their own gestures. It waits for the swipe and the lift of the row under the finger and never starts on a switch; the 12 pt gap between cards belongs to the nearest card through the touch tolerance. From iOS 18 it names the row's recognizers; before, the row's swipe is a SwiftUI drag, and SwiftUI holds the pan until that drag fails or takes the touch, which is measured, not expressed in our code. Measured on iOS 17.5, 18.5 and 26.5.
- `ReorderableRows` measures every row, so it never sits in a lazy container, and only inside a `CardScrollView`, the one place that injects `RowInteraction`.
- Swiped and reordered rows read only the items their list captured: a row that reads the store observes them on its own and is redrawn apart from the list while a drag settles, showing the wrong item.

## Time

- `keepScreenOn` is on by default. A timer prevents automatic screen lock only while this preference is on and its countdown or a timed stage is running; a paused, waiting or finished run lets the screen lock. Its awake vote follows preference changes without restarting the clock.
- UI must call `WorkoutRun.tick(at:)` and then `snapshot(at:)` on every update; `snapshot` alone never commits progress.
- Never convert between `Date` and `Duration` outside `TimeMath`.
- `rebase(at:keepingTotalElapsed:)` is the recovery point after a backward clock change.
- The timer runs at most one clock loop, a 3-2-1 countdown or a tick loop. Each loop carries a generation in its cancel id and in every action it sends; an action from an older generation only cancels its own loop.
- A loop only sleeps and wakes; the reducer measures and commits. Before every tick and user action it checks the clock anchor, a wall date and a `continuousClock` instant read together and refreshed on every tick, through `TimeMath`'s public `Date.elapsed(since:)`. A backward jump rebases the run to the progress the monotonic clock vouches for; a forward jump is logged and kept, like time in the background.
- `snapshot` without `tick` appears in two places only: the tick loop's own copy of the run, which schedules wake-ups and is never shown or committed, and the state's initial snapshot at `.distantPast` of a run that is idle or finished.
- A tick loop that ends while the committed run still runs reports `isFinal`, and the reducer starts a new one.
- One clock instance per timer session: a `MonotonicInstant` checks only the type of its instant.
- `WorkoutTimerStack` forwards `scenePhase`; the run continues through `.inactive` (Control Center and the App Switcher), while signals stop until `.active`. Leaving resets a 3-2-1 to its full length and runs no countdown until the app is back, then counts it from 3. A running run takes a fresh anchor as it leaves, so on return the same process's anchor measures the time away and a clock moved back is rebased. Every write is under a background-task assertion; what the file holds is the newest write that completed.
- Across a process restart only the record's `sinceEpochMs` survives: a clock moved back past it re-anchors at the saved position, a smaller backward move undercounts, a forward one counts as elapsed time (`docs/timer-engine.md` › Saved runs).

## Domain limits

Anything that edits a workout applies `WorkoutLimits.normalizedStages(_:)` and `normalizedTrainingRounds(_:)`, and UI limits match `WorkoutLimits`. Otherwise the user would see stages that never reach the schedule.

A stage name may be empty; anything that displays a stage shows its intensity name instead. Storage keeps the empty name, so the fallback follows the current language.

New input of a workout or stage name goes through `WorkoutLimits.limitedName(_:previous:)`: at most `maxNameLength` characters, an edit past it rejected whole. A longer name stored before the limit shows in full, also in the Live Activity, which never cuts a name by length; an activity over the 4 KB limit ends and the timer shows its footnote. While it remains over the limit, any edit is accepted only if it reduces the character count, including a replacement with unrelated shorter text; an edit of the same length or longer is rejected whole.

## Snapshot tests

- Harness regression tests run separately from the 34-PNG screen matrix: the package's `SnapshotCaptureTests` and the app-hosted `CircuitTimerSnapshotContractTests`. The latter shares only the screen tests' `Support` sources and uses synthetic references it removes after every case. Keep contract tests out of `CircuitTimerSnapshots`, whose run checker requires every case to correspond to a screen reference. Environment overrides are scoped and restored; the contract suite is serialized because UIKit windows and process environment belong to the process. Serialize these two commands manually per checkout, including across simulator destinations: temporary reference directories are shared between those processes. Their generated PNGs are ignored if a process is interrupted. Dedicated ru/de processes fail unless their selected language test passes without a skip.

How to add one, step by step: `docs/testing.md` › How to add a snapshot.

- A snapshot is a state plus a text size. A test builds the `AppFeature.State` the screen shows after its transitions — the Workouts stack's `path` and the editor's `phase` set directly through `@testable import`, never reached by `send`s — and passes it to `assertAppSnapshot(textSize:)`. The timer's cover does not draw in the first frame, so a timer test builds a `WorkoutTimerFeature.State` with the factories in `Support/WorkoutTimerFeature+SnapshotStates.swift` and passes it to `assertTimerSnapshot(textSize:)`, which draws `WorkoutTimerStack` as the window's root with the real reducer and no tab bar. Each factory ends by settling the state as the screen shows it once it has appeared (its first `.task`, notification access, an active scene and the signal baseline), a fixed point of the timer's appear actions, so they change nothing on screen; a contract test drives the reducer's real appearance from the state before each factory and compares it with the factory. `assertTimerSnapshot` refuses a state that is not such a fixed point, and pins `scenePhase` to `.active`: a hosting controller installed as a window's root sits outside the host's `WindowGroup` and reads SwiftUI's default `.background`, which would restart the countdown's audio preparation or reset the signal baseline. The timer's root has no tab bar, so nothing checks its stack depth: only the reference shows that the stage list is pushed. One test function per state, named `test_<screen>_<state>_matchesReference` and unique across the snapshot tests; it always takes text sizes, and only text sizes, as its arguments. Keep its `@Test` declaration on one line, using `SnapshotTextSize.currentCases()` or `SnapshotTextSize.currentCases(in: [.large])`, so the run check can enumerate the expected sizes.
- Variants: the language comes from the test process, and `make test-snapshots` runs four processes (`en`/`ru` × `large`/`ax5`), because language and UIKit's preferred font size are process settings; the text size is `large` or `ax5` (`accessibility5`); dark only. The scheme supplies `-UIPreferredContentSizeCategoryName` from `SNAPSHOT_CONTENT_SIZE_CATEGORY`. `SnapshotTextSize.currentCases()` selects that process's arguments through `SNAPSHOT_TEXT_SIZE`; use `currentCases(in: [.large])` for large-only states, which have no AX5 arguments. Every applicable case still has to compare; an unexpected skip fails the run. The capture validates the actual process category against its argument before creating the screen, and the journal records it for the run check. The full-matrix commands narrow a run only by language: the committed references and the test functions are the list of expected cases, so a narrower or repeated run would misreport them. References are `CircuitTimerSnapshotTests/__Snapshots__/<test file>/<test function>.<language>-<size>.png`, 1206×2622 px, recorded only on `iPhone 17` / iOS 27.0; the run check reads the device's platform, model and OS from the result bundle.
- Local iteration: `make test-snapshot TEST=<function>` compares one `en`/`large` variant by default; `SNAPSHOT_LANGUAGE=en|ru` and `SNAPSHOT_TEXT_SIZE=large|ax5` select another. `make record-snapshot` records only the selected variant when needed and compares it again. These targets are refused with `CI=true`; CI and `make ci` keep the full matrix. Selection resolves the unique source function to its explicitly annotated `@Suite` under `SnapshotTests`, rejects unsupported sizes before Xcode, and requires one executed case with one journal row. A partial run never counts as full-matrix evidence. Recording keeps the full command's device and clean-reference guards.
- `SnapshotCapture` works out the variant from the process and validates the test's text-size argument against its launch configuration and actual UIKit category. For every mount `assertAppSnapshot` (or `assertTimerSnapshot`) builds the state, checks it and creates its store inside one `withDependencies(SnapshotDependencies.prepare)`, so the state's shared preferences and the store see the same values, and derives from that same state the root and the tab bar expectation; `SnapshotCapture` does the rest. It mounts the root in its own 402×874 pt window at scale 3 in the host's active scene. The variant's traits go on the window as well as on the root, so presented controllers inherit them. These traits alone do not set UIKit's process font size: each process also launches with its explicit content size category, which the capture validates. When the state has the Workouts tab selected over a pushed screen, the tab bar is hidden with `setTabBarHidden(true, animated: false)`, as `TabBarRidesWithRoot` does on a push it never sees here; a UIKit stack or bar that does not match the state fails. It waits one main run-loop turn and draws the window with `drawHierarchy`. The reference is that first frame. `SnapshotImageComparison` normalizes both images to 8-bit sRGB: pixel dimensions and alpha bytes match exactly, RGB channel deltas are at most 2/255, and at most 1/80 (1.25%) of pixels differ; exceeding either bound fails. Both mounts use this same strategy, which keeps SnapshotTesting's PNG coding and failure attachments. Keep both limits when changing the comparison: a small changed area alone could hide a high-contrast regression.
- As a safeguard against Liquid Glass drawing another first frame, on a mismatch the window comes down, the state is mounted again from scratch in a fresh one, and only that comparison counts; `check-snapshot-run.sh` names every snapshot that needed it. No fixed sleeps or readiness checks. The bounded comparison intentionally accepts small low-amplitude color changes within both limits, regardless of whether their cause is rendering noise or an intentional edit.
- Dependencies are the test context's except what `SnapshotDependencies` sets: in-memory preferences, a `TestClock` nothing advances, authorized notification access. The timer's entry adds `TimerSnapshotDependencies`: the preview values of every client the timer reaches, as `AppScenario.prepare` sets them, a constant `date`, `preferredLocales`, an incrementing `uuid` and an empty `dismiss`, all set by the test entry (the host links no module). Lint checks only `AppScenario.prepare`, so a new client the timer reads also needs a line in `TimerSnapshotDependencies`. These are rendering tests, not exhaustive effect tests. Unconfigured dependency endpoints keep their test values; a passing snapshot does not prove that no effects ran. The host never configures TipKit, so tips stay hidden.
- A snapshot fails, instead of drawing, for a state with a presented destination (the timer's cover does not draw in the first frame; alerts and dialogs, the timer's close dialog among them, are not supported yet), for a timer state that is not a fixed point of its appear actions, for another runtime or screen geometry, a reference that does not load or has the wrong size, and a process whose language is not `en` or `ru` or not the main bundle's, or whose text-size launch configuration and UIKit category do not match its argument. Every such error is written to the run journal before it fails the test, and its message names the runtime build.
- References are written only by `make record-snapshots` or local `make record-snapshot` (`failed` mode); comparison commands and CI use `never`. Every changed PNG is reviewed in its pull request. Snapshots do not guard how the tab bar leaves on a push.

## Persistence (CT-2, CT-5)

- Domain types never become `@Model` types; persistence maps to and from them.
- Durations are stored as `Int` milliseconds.
- CloudKit sync: no `@Attribute(.unique)`; every property optional or defaulted; relationships optional; stage order kept in an explicit `order` field. Once a schema is deployed to Production, later versions only add.
- Schema V2 adds `WorkoutModel.copyID` (set once from `@Dependency(\.uuid)`, assigned to older records on the next read) and `isFreshSample` (a sample seeded here, cleared by its first save); V1→V2 is lightweight.
- Of the readable copies of one `workoutID` the one with the lowest `(isFreshSample, copyID)` shows; the others stay stored, are not counted as hidden and are never deleted on read. Stored order is `(order, workoutID, copy rank, persistentModelID)`, stages break ties by `stageID`.
- Deleting a workout deletes every copy and writes a `SeedMarkerModel` keyed `deleted:<id>`; a marked workout is hidden, its late copies are removed, the sample is not seeded again, and `save` returns `.deletedElsewhere`. Deletions before CT-5 were local and have no marker.
- Every `WorkoutStore` operation runs in a `ModelContext` of its own, so it sees what an import changed.
- A saved run is `WorkoutRunRecord` v1 with explicit `CodingKeys`: `schemaVersion`, `workoutID`, `scheduleFingerprint`, `phase`, `positionMs`, `cursor`, `sinceEpochMs`. The fingerprint is a SHA-256 of the normalized schedule structure (index, section, round, round count, kind, stage id, duration in ms; not the name). On restore, rebuild the schedule and drop the record if the fingerprint differs or `cursor` is out of range.
- Run records live outside SwiftData: one JSON file in Application Support (`RunRecord/WorkoutRun.json`), excluded from backup on a best-effort basis. The body is exactly the v1 record.
- Writes go through one actor on a dedicated serial queue executor, in the order of a revision the reducer takes from `nextRevision()`; a failed write leaves the file as it was and is retried at the next sync, and until one succeeds the timer warns that the run may not come back or may come back in an earlier state. These writes have no `CancelID`: the revision orders them, and an in-flight write must finish. Reads open the file on their own queue.
- The timer writes its run on every clock sync — every operation, jump and change of status, and every time the app leaves the screen — but not on a tick that changes none of them, and clears it after the cover is dismissed; `AppFeature` clears it once more when the cover goes.
- At launch `AppFeature` cleans notification requests from previous process owners in parallel with reading the record; cleanup never delays the restore deadline. It reads the record, racing the read against a 2 s timeout, and then loads the workouts; the restore decision is made at the first load, before another screen can be opened. A run that ended while the app was gone, or a paused one older than 24 hours, is dropped silently. A record that cannot be restored (workout changed or gone, file corrupt, unreadable or from another version) shows one alert; only a corrupt file is removed. A stall while reading shows that alert before the app knows whether a file exists — accepted. Otherwise the list asks «Continue the workout “<name>”?»: Continue settles the run at the tap and opens the timer in its saved phase, after the alert has gone. The accepted record stays until the cover appears; if presentation fails, an error offers Retry (settled at the new tap, with a fresh timer owner) or Finish in the same session. Finish clears the record and says so if that fails. iOS keeps the scene session after an App Switcher swipe (seen on iOS 26.5 and 26.7.1), so the app cannot tell a force quit from a system kill or a crash: every process death asks, and a return from the background never does.

## iCloud sync (CT-5)

- `CloudSyncClient.mirroredContainer()` decides once per process from the switch and `CTCloudKitContainerIdentifier`; `WorkoutStoreProvider.live()` opens the same file with `.private` or `.none`, falls back to `.none` if CloudKit fails to open, and reports `storeOpened`. A switch change applies at the next launch.
- Unsigned builds pass `CT_CLOUDKIT_CONTAINER=` (`UNSIGNED` in the `Makefile`): a `CKContainer` without the entitlement traps, and an unsigned `.private` store opens without complaint. `CloudSync` reads the account, and so creates a `CKContainer`, only for a store that opened mirroring.
- `remoteChanges()` follows successful imports and setups, account changes and the account read that follows one; `AppFeature.outsideChange` reads the list again unless a write, a reload or the first load will. After a load a read-only workout screen shows the stored version or closes when the workout is gone; drafts, alerts and a Start on its way are left alone. No reload on `.active`: activation imports post their own event.
- Settings' footnote: a pending relaunch first, then «only on this device» while off, then the problem (failed open, account, quota, sync failure).
- `CloudSyncClassification` maps errors; Core Data's Cocoa codes 134400, 134406, 134419 and 134417 are undocumented and taken from Apple engineers' forum answers.
- `-CTInitializeCloudKitSchema` in a signed Debug build creates the Development schema and exits before the app's store opens. Deploy it to Production before a release tag.
- How it works, the accepted limits, the experiments and the device checklist: `docs/icloud-sync.md`.

## Signals

- `TimerPreferences` keys never change and contain no dots; all signals are on by default.
- `CueEngine` owns the audio session and outputs on one private serial queue. State methods check `dispatchPrecondition`; never use `assumeIsolated`, which cannot verify that executor on iOS 17.
- Narrow exception to injected clocks: its 1.5-second idle deactivation uses an `AnySchedulerOf<DispatchQueue>` passed to the initializer, live on the engine queue. The deadline must survive cue task cancellation; no reducer timing depends on it.
- While the session is active and no output plays, one valid idle deadline is pending. Admission replaces it, successful output start invalidates it, and completion reschedules it. Errors keep it alive.
- A cancelled task stops waiting; a newer revision, owner-scoped suspend/end, resign-active or the idle deadline stops audio and releases ducking.
- Tones are reproducible 44.1 kHz mono PCM WAV resources; regenerate with `swift scripts/generate-cue-tones.swift` from the root.
- `SignalTrack` compares settled snapshots once per reducer action and emits at most one event: countdown digit, finish, new stage (with name), same-stage resume (without name), or the current last three seconds. No skipped event is replayed.
- A fresh or resumed countdown beeps its current digit once. A restored running run is a silent baseline; a restored paused run announces the stage on resume. Returning from an inactive scene marks the current stage as seen.
- Foreground signals run only in an active scene with the timer visible, outside its stage list and close alert. Leaving clears the baseline and haptic and suspends through the last cue revision.
- A VoiceOver-only cue preempts without activating audio, then posts a low-priority announcement only while active and uncancelled. Speech uses the app language; an absent voice reports a failure instead of falling back to another language. `Speech.xcstrings` owns Work/Rest/Pause.
- Each foreground switch gates only its output; Sound also gates the system sound of a background notification. Haptics are state revisions consumed by `.sensoryFeedback`; failure kinds are cleared only by a result proving that output recovered. Signal failures never stop the workout.

## Background notifications (CT-3-5)

- `signalBackgroundNotifications` is a separate, default-on preference. First Start requests alert/sound permission before creating the timer; Continue of a saved run never prompts. A delayed request offers Start now / Wait without treating a slow user as a failure.
- `BackgroundNotifications` holds one foreground delegate installed through its client in `CircuitTimerApp.init`. It suppresses the module's presentation in foreground; background delivery belongs to iOS.
- The timer projects at most 32 stage starts/finish events, ending at a manual pause, on every settled action. State stores only a compact key; payloads belong to effects/client. A truncated window adds an open-app notice to the last real event. No last-three-second background cues, speech or independent haptics.
- The client fences physical identifiers by owner/revision, protects active owners from late orphan reads, and removes stale add completions by their own ID. End installs a tombstone before dispatching removal. iOS does not acknowledge removal.
- A fresh pending snapshot verifies still-future coverage; imminent missing requests remain unconfirmed and are not replayed. Retry uses injected monotonic time (10 seconds), plus active-scene reconciliation. Cleanup waits at most 500 ms per caller and coalesces/rate-limits physical sweeps to 30 seconds.
- When iOS terminates the app, `beginTermination` ends every owner and refuses later ones before it returns, and `finishTermination` removes the module's requests iOS still lists (see Apple Health). An add admitted just before may still land; the next launch's cleanup removes it.
- Already scheduled requests may fire after suspension or a process death iOS does not report (see Apple Health). The app cannot refill the window or repair clock changes until it runs again. Delivery time, Focus, silence, system sound and vibration follow iOS settings. Notification failures never stop a workout or hide record/audio/voice failures.

## Live Activity (CT-4)

The reader's view of the controls and the device checklist are in `docs/live-activity.md`; change it together with this section.

- The timer syncs its Live Activity after every action once its clock has started and its owner-scoped control subscription is ready, not only on a clock sync: a stage that ends on a tick reaches the Lock Screen without a record write or a new loop. `ContentState(run:at:)` ticks a copy and reads its snapshot and `outlook(at:)`. The start countdown reads as `getReady`, the resume countdown as `paused`.
- The content is the running stage with its boundary dates and the next stage with its end. `staleDate` is the stage end. The display counts the stage down by itself, and the next stage counts from the stage end by itself. Once iOS marks the content stale it shows the next stage and asks to open the app for anything after it. iOS redraws stale content no earlier than about two minutes after the last update (measured on iOS 17.5 and 26.5). A held stage shows a fixed time: `Text(timerInterval:pauseTime:)` with a future `pauseTime` does not hold, so there is no workout total.
- A counting `Text(timerInterval:)` has no width of its own and breaks a layout under `fixedSize`; the clocks take the width of a hidden template of League Gothic's widest digit and win over names.
- `LiveActivityCoordinator` owns everything else: one queue per owner that applies the newest revision on a loop a cancelled caller does not stop, content it already shows is never sent again, and a finished run ends the activity with the standard dismissal; its final card stays, also through later syncs, until `end(owner)`. The live transport keeps the activities this process requested, so an update or end reaches one that iOS has not listed yet. `end(owner)` installs a tombstone, removes the activity at once and waits at most 500 ms. The timer calls it on every close path before `dismiss()`, and `AppFeature` again when the cover goes another way. `endOrphans` runs at launch in parallel with reading the run record and never delays it.
- `sync` returns a `LiveActivityNotice` only when the footnote should change; the reducer accepts it only with a larger `serial`. Live Activities off before the timer's first activity: nothing shows and no footnote, and once they are turned on the next sync starts one. An activity that goes while it shows, removed by the user or ended by iOS when they are turned off, does not come back for that timer, also without a footnote. A failure no retry can fix (over 4 KB, unentitled, unsupported) ends the activity and keeps the footnote. Others retry on the next sync. An activity iOS has not listed 10 s after its request is ended and requested again on a later sync, so two never show.
- No background assertion, push server or audio mode; a workout session keeps the app running instead (see Apple Health). At termination `beginTermination` refuses every later request and update, and `endAll` tombstones every owner and ends every activity immediately twice, before and after the drains already under way, so a finished card ending with the standard dismissal goes too. Accepted limits: the finished card stays until the timer closes or iOS removes it; an activity of a process that dies without `applicationWillTerminate` (a crash, a kill of a suspended app, a swipe once iOS 17–25 has suspended it) stays until its control is tapped or the next launch; StandBy, the watch Smart Stack (iOS 18) and CarPlay (iOS 26) show the same views without separate checks.
- `WorkoutTimerStack` owns the control subscription; readiness gates card publication, never the original clock startup or permission refresh. Intents carry the exact activity ID, direction and `controlGeneration`. The coordinator admits one request per owner, checks the app process before any deletion, and bounds the caller's wait to 5 s. Cancellation or timeout stops waiting, not an admitted command or its syncs. Unknown owners end only that matching activity, with at most 500 ms of waiting; no run record is read or changed.
- The reducer always reconciles time before accepting or rejecting a card command. Pause applies only to running; Resume immediately continues paused/awaitingUser, drops a resume countdown and clears both the stage list and close dialog. Initial get-ready and finished runs cannot start or skip through a card. Generation changes on control transitions, including automatic resume-countdown completion and entry into a manual pause, but not ordinary ticks or scene changes. This fences an old Resume after the run returns to a different pause.
- An applied command is acknowledged after the actual ActivityKit drain and the newest required notification sync complete. Superseded work waits for the newer result; a nil footnote is not proof of success. Partial notification failure leaves the command applied with the existing warning. Record writes, their revisions and their background assertions remain unchanged, and acknowledgement never waits for disk. No new background assertion is taken for intent execution; after the 5 s deadline iOS may still suspend the app with the old card or notification window.
- The Lock Screen and expanded Dynamic Island show one Pause/Resume button beside the clock, with a 44 pt DesignSystem target. The colored card uses `tone.ink`, the Island `tone.accent`; compact/minimal, get-ready and finished show no button. Stale timed/manual/finished projections choose Pause/Resume/no button respectively. Card state requires `controlGeneration` when decoding; there is no compatibility path for cards created before CT-4-2.
- App/UI-test builds run `scripts/check-activity-intents.py` against both compiled hosts: hidden Pause/Resume, ID/generation, background/main policy and no package re-export. This guards the iOS 17 metadata lookup regression without introducing live clients into UI test scenarios.

## Apple Health (CT-11)

- A running `HKWorkoutSession` (background mode `workout-processing`) keeps the app running in the background, so an App Switcher swipe reaches `applicationWillTerminate`, which removes the cards and notifications (measured on iOS 26.7.1: over 3 minutes in the background, then the swipe). Sessions exist only on iOS 26 and later with Health access; `HealthAccess.unavailable` covers earlier versions and devices without Health.
- Access is write-only to the workout type and asked once, at the first Start, after the notification stage and before the timer: `StartIntent.stage` moves to `health`. Whatever Health answers, or if it cannot be asked, the timer opens; iOS never says whether writing was allowed. The sheet is asked only in an active scene; a stage that has not finished within 10 s of an active scene, reading the access or waiting for the sheet, frees Start, and a new tap opens the timer without Health. A late answer opens the timer only while its Start is still current; a changed workout makes it stale. No alert, footnote or setting; Continue never asks.
- The timer starts its session once its clock has started, in an active scene, on `.task` and on every return to `.active`: HealthKit refuses a start in the background, and the client ignores repeats and owners that have ended. Pauses, the stage list and the close dialog leave it running. HealthKit ending a running session marks it lost without a retry, which would split the workout. A session asked to end stays held until HealthKit reports it ended: one that was still starting is ended again once it runs. `WorkoutSessions` reaches HealthKit only through `SessionTransport`, so its rules can be tested without Health. Always `highIntensityIntervalTraining`, indoors.
- The timer follows its run in a `WorkoutHealthTrack` after every action, in wall-clock dates: running until the run's `automaticStopDate`, halted (a pause by the user or the schedule, the resume 3-2-1, the stage list, the close dialog) or finished. The track starts when the run first runs: after the start 3-2-1, at a restored running run's first action, or when a restored paused run resumes. Every change goes to `sync` with a revision; `WorkoutSessions` keeps each owner's newest track, with or without a session, and ignores older revisions, owners that have ended and owners whose session was lost, except for the first track after a loss that came before any track, whatever its revision (see below). A backward clock jump the timer measures moves the whole track with the run's `rebase`, so the time counted stays; a date before the newest one the track holds means the clock went back unmeasured, and the track moves back the same way, so the running time since its last transition is lost, up to the whole workout. A forward jump counts as running time, as in the run. The track lives only in the timer's state and the actor: the run record is unchanged (see Persistence).
- Ending a held session saves one workout per owner: `end` projects the track onto the closing date and saves it with a detached `HKWorkoutBuilder` (same configuration, the local device), with a pause and a resume event around every pause, so Health leaves the pauses out of the duration. The session's own builder is discarded: a detached one needs no session, so `end()` keeps its order and timing and the save runs beside it. The workout begins when the run first ran and ends at the close; a close from a pause ends at the pause's start, and a run that finished ends where it finished, also when no tick saw it. A workout of zero length is not saved. It carries no samples. `finishWorkout` returning nothing without an error means it was saved while the phone was locked, logged as a notice. A failed save is logged; no retry, alert or footnote.
- Only a timer that held a session saves: on iOS 17–25, without write access or when every start failed before the close, nothing is saved; a close while the session is still starting saves, as the detached builder needs no session. A session HealthKit takes away saves the workout up to the date HealthKit reports for a stop or an end, or up to the moment `WorkoutSessions` handles a failure such as another app's start, which has no date; the close then saves nothing more. The loss is built from the newest track that has arrived, projected onto the present and cut at the loss, so a transition whose `sync` comes later is not in it; a loss before any track has arrived waits for the first one, or for the close, and saves it up to the loss. In the background iOS suspends the app about 16 s after a takeover, which can cut that save short. Continue of a saved run is a new owner and a second workout; the time between the process's death and Continue is in neither.
- At launch `AppFeature` calls `endOrphans` beside the record read: a session an earlier process left running is ended and discarded, saving nothing, never one of this process, compared by its activity's UUID. A start waits at most 2 s for that recovery.
- A new session ends the one running, ours or another app's: measured on iOS 26.7.1 with two apps, the earlier session failed with `errorAnotherWorkoutSessionStarted` within 10 ms of the later start. So a timer's Start ends another app's workout session, such as Fitness's, and iOS offers no way to see one first; accepted. A timer whose session another app takes keeps running without it until it closes and never takes it back, and in the background iOS suspends it as on iOS 17–25 (about 16 s after the takeover). A start that fails the same way tries again only at the next active scene.
- At termination `AppDelegate.applicationWillTerminate`, on every iOS version, takes a 2 s deadline before `ProcessTeardown.begin()`, which synchronously closes the notification, Live Activity and Health gates. `run(at:)` then runs on a detached task: the Live Activity `endAll` (at most 1 s) and the notification barrier (at most 300 ms) together, then Health `endAll`, which saves each held session's workout from its owner's newest track at the termination date and waits, with what is left, for every session to report its end and every save to finish. Each limit cancels its side without awaiting it. The main thread waits on a semaphore until the deadline; none of our code it waits for needs the main thread; that ActivityKit, HealthKit and UserNotifications do not need it either is an assumption, not a measurement. The run record stays, so the next launch asks to continue. On iOS 17–25 iOS delivers the callback only while the app still runs, for example in its short background window.
- Accepted limits of the workout saved at termination:
  - `applicationWillTerminate` holds the main thread, so the last `sync`s, possibly several, may not have reached `WorkoutSessions`: their effects had not started, or they arrived after `endAll`. The workout is built from the newest track that arrived. A pause it missed counts as running until termination, a resume it missed drops out, a start it missed saves nothing; a missed finish is covered by the run's stop date. The error runs from the first missed transition to termination, except that a missed measured rebase can shift the track further, up to dropping the workout.
  - A loss HealthKit has delivered but `WorkoutSessions` has not handled yet is overtaken by `endAll`: the workout then ends at termination. A session HealthKit stopped is asked to end and released at once, so `endAll` waits for its save but not for its end.
  - A save longer than what is left of the 2 s dies with the process. A process that dies without `applicationWillTerminate` (a crash, a kill of a suspended app) saves nothing, and the next launch discards its session as an orphan.
- What is saved and the device checklist are in `docs/apple-health.md`; change it together with this section.
